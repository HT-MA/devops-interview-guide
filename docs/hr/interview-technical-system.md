# 系统设计面试 Q&A

系统设计（System Design）在 DevOps/SRE 面试中的比重越来越高。和软件开发岗位的系统设计不同，SRE 的系统设计更关注：可观测性、可靠性、成本效率、自动化程度和运维复杂度。

以下题目均来自一二线互联网公司的真实面试记录，涵盖 Google、Meta、阿里、腾讯、字节跳动等公司。

每个问题的答案遵循以下框架：
1. 需求澄清（Clarify Requirements）
2. 整体架构（High-Level Design）
3. 关键设计决策（Key Design Decisions）
4. 深度讨论（Deep Dive）

---

## Q1: 设计一个监控 1000+ 微服务的可观测性系统

**难度**: ⚫⚫⚫ 高级 | **面试公司**: 字节跳动、腾讯、Meta、Uber

**问题原文**: "Design a monitoring system for 1000+ microservices." / "设计一个覆盖上千微服务的监控系统。"

**回答**:

**1. 需求澄清**

先和面试官对齐范围。我会问几个问题：
- 监控的维度是什么？（Metrics、Logs、Traces——即三大支柱）
- 微服务的部署方式是什么？（K8s 还是虚拟机）
- 数据量大概多少？（平均每个服务每秒产生多少指标、日志量）
- 告警需求：什么级别的告警需要多快的响应？
- 历史数据需要保留多久？

典型假设：1000 个微服务，部署在 5 个 K8s 集群上，每个服务每秒暴露 200 个指标，每天产生 50TB 日志，需要保留 30 天。

**2. 整体架构**

```
┌─────────────┐    ┌──────────────┐    ┌─────────────┐
│  Metrics Path │    │  Logs Path    │    │  Traces Path │
├─────────────┤    ├──────────────┤    ├─────────────┤
│  kube-state  │    │  Filebeat/    │    │  OpenTelemetry│
│  metrics     │    │  Fluentd      │    │  Collector    │
│  node_exporter│    │              │    │              │
│  custom      │    │              │    │              │
│  metrics     │    │              │    │              │
├─────────────┤    ├──────────────┤    ├─────────────┤
│  Prometheus  │    │  Kafka        │    │  Tempo/Jaeger│
│  + Thanos    │    │  (缓冲层)      │    │              │
├─────────────┤    ├──────────────┤    ├─────────────┤
│  Cortex/    │    │  Loki/ES      │    │              │
│  Mimir      │    │              │    │              │
├─────────────┤    ├──────────────┤    ├─────────────┤
│  Grafana    │    │  Grafana      │    │  Grafana     │
│  + Alertman.│    │  + LogQL      │    │  + TraceQL   │
└─────────────┘    └──────────────┘    └─────────────┘
```

**3. 关键设计决策**

**Metrics 路径**：

- 选 Prometheus + Thanos（或 Grafana Mimir）而非单机 Prometheus。1000+ 服务远超单机 Prometheus 的能力上限（一台 Prometheus 合理支撑 100-200 万时间序列，1000 微服务 × 200 指标 = 20 万时间系列，加上每个 Pod 的容器指标约 100 万，已经接近极限）
- 采用 Prometheus Operator 的 ServiceMonitor 自动发现，不需要人工配置每个服务的指标端点
- Thanos 的 Store Gateway 实现长期存储到对象存储（S3/MinIO），解决了 Prometheus 的数据持久化和全局查询问题
- 告警使用 Alertmanager 的分组和静默机制，防止告警风暴

**Logs 路径**：

- 使用 Fluentd/FluentBit 以 DaemonSet 方式采集容器日志，发送到 Kafka 做缓冲
- 下游消费端使用 Loki 而非 Elasticsearch。原因是：1000 微服务的日志检索场景多数是"根据 Label 找到某个服务的日志然后搜索关键词"，Loki 的 Label 索引方式天然适合这个模式，且存储成本远低于 ES
- 对于需要全文检索的审计日志场景，保留一个独立的 ES 集群

**Traces 路径**：

- 使用 OpenTelemetry SDK 做自动埋点，通过 OTel Collector 做采样和路由
- 采样策略：高流量服务使用"头采样 + 基于错误率的自适应采样"，低流量服务全量采集
- 存储使用 Grafana Tempo 或 Jaeger，后端存储用对象存储

**4. 深度讨论 - SRE 面试会追问的问题**

**Q: 怎么避免告警风暴？**
A: 三层手段：第一，Alertmanager 的分组机制——K8s 节点宕机导致的 100 个 Pod 不可用，合并成一个告警。第二，依赖关系感知——如果一个服务挂了并且它的依赖也挂了，只上报根源服务的告警。第三，维护窗口期内自动静默。

**Q: 多集群场景下怎么做全局视图？**
A: Thanos Query 层提供了全局查询的入口，Grafana 的 Data Source 指向 Thanos Query 即可跨集群查询。关键点在于：所有指标必须带有统一的 cluster Label，保证全局查询时可以区分数据来源。

**Q: 数据量如果再翻 10 倍，瓶颈在哪里？**
A: 第一个瓶颈在 Prometheus 的 scrape 能力——每个 Prometheus 实例的 scrape 目标数量有限。解决方案是使用 Prometheus 的 hashmod 分片，将目标分散到多个 Prometheus 实例。第二个瓶颈在 Thanos Store Gateway 的查询性能——可以通过添加 Compactor 组件做 downsampling，以及增加 Store Gateway 的副本。

## Q2: 设计一个微服务架构的 CI/CD 流水线

**难度**: ⚫⚫⚫ 中级 | **面试公司**: 阿里、字节跳动、快手、美团

**问题原文**: "Design a CI/CD pipeline for a microservices architecture." / "设计一个支撑 100 人开发团队的 CI/CD 系统。"

**回答**:

**1. 需求澄清**

- 团队规模：100+ 开发人员，50+ 微服务
- 部署频率：每天 50-100 次部署
- 部署策略：要求零停机部署，支持灰度发布和回滚
- 环境：开发、测试、预发布、生产

**2. 整体设计**

```
Git Push
   │
   ▼
┌─────────────┐
│  CI Pipeline │
├─────────────┤
│  Code Lint   │
│  Unit Test   │
│  Build Image │
│  SAST Scan   │  ← 安全扫描（Trivy/Snyk）
│  Push to     │
│  Registry    │
└──────┬──────┘
       │ 触发方式: PR Merge 自动触发
       ▼
┌─────────────┐
│  CD Pipeline │
├─────────────┤
│  Deploy Dev  │  ← 自动
│  Deploy Stg  │  ← 自动（性能测试）
│  Deploy Prod │  ← 需要审批 + 灰度
│  Smoke Test  │
│  Health Check│
└──────┬──────┘
       │
       ▼
   ArgoCD / Flux (GitOps)
```

**3. 关键设计决策**

**CI 层设计**：

- 使用 GitHub Actions 或 GitLab CI。避免自研 CI 引擎——这是成熟的领域，不需要重新发明轮子
- 每个微服务有一个独立的 CI 配置文件，但共享一个公共的 CI 模板库（reusable workflow）
- CI 流水线的核心原则：尽量快（控制在 10 分钟以内）。手段包括：依赖缓存、并行执行、增量构建（只构建变更的模块）
- 镜像 Tag 策略：使用 Git commit SHA + 时间戳，而非 `latest`。确保每个镜像可追溯

**CD 层设计**：

- 采用 GitOps 模式（ArgoCD 或 Flux）。Git 仓库是基础设施状态的"唯一真相来源"（Single Source of Truth）
- 部署策略：对于无状态服务，使用滚动更新（Rolling Update）+ Readiness Probe 保证零停机；对于关键入口服务，使用金丝雀发布（Canary Release）
- 更细粒度的流量控制使用 Service Mesh（Istio）的 VirtualService —— 1% -> 10% -> 50% -> 100% 逐步放量
- 自动回滚机制：如果新版本在 10 分钟内出现了错误率上升或延迟增加，自动触发回滚

**环境管理**：

- Dev 环境：每个 PR 自动创建 Preview Environment（Ephemeral Environment），在 K8s namespace 中部署，PR 合并后自动清理。这解决了"环境不够用"的痛点
- Staging 环境：和生产环境架构一致但规模缩小（比如 1/10 的副本数），运行集成测试和性能测试
- Production 环境：生产部署需要人工审批（至少 senior engineer 确认），但 CI/CD 平台提供一键部署和一键回滚的能力

**4. 深度讨论**

**Q: 怎么保证 CI/CD 系统本身的可靠性？**
A: CI/CD 系统是开发流程中的"关键路径"——如果 CI/CD 挂了，整个开发流程就停了。保障措施包括：CI Runner 多可用区部署、Runner 自动扩缩容、以及 CI/CD 系统的变更也要走 Code Review。

**Q: 微服务之间的依赖怎么处理部署顺序？**
A: 有两种方案。方案一：每个服务独立部署，通过 API 版本兼容（向后兼容）来保证依赖服务先更新或后更新都没问题。方案二：使用 ArgoCD 的 Sync Waves 或 Spinnaker 的 Pipeline 依赖。推荐方案一——如果每个服务都需要按顺序部署，就失去了微服务的灵活性。

**Q: 数据库变更怎么处理？**
A: 数据库 schema 变更必须和代码部署分开，不能放在同一个 CI/CD 流水线中。建议使用专门的迁移工具（如 Flyway、Liquibase），且迁移操作必须做到向后兼容（加列而不是删列、加索引不要锁表），具体的数据库迁移方案参考 Q3。

## Q3: 设计一个零停机数据库迁移方案

**难度**: ⚫⚫⚫ 高级 | **面试公司**: 阿里、腾讯、字节跳动、Google

**问题原文**: "How would you handle a database migration without downtime?" / "设计一个不停机迁移 MySQL 数据到新集群的方案。"

**回答**:

**1. 需求澄清**

- 源数据库：MySQL 8.0，单库 2TB，主从架构
- 目标：迁移到新的 MySQL 集群（也可能是分布式数据库如 TiDB）
- 迁移期间业务不能停（RTO=0，RPO≈0）
- 迁移窗口：没有"凌晨停机"的时间窗口

**2. 整体架构**

```
                    ┌──────────┐
                    │  Application│
                    └─────┬────┘
                          │
              ┌───────────┴───────────┐
              │                       │
              ▼                       ▼
        ┌──────────┐          ┌──────────┐
        │ Old MySQL │◄────────►│ New MySQL │
        │ (Master)  │   Sync   │ (Master)  │
        └──────────┘          └──────────┘
              │                       │
              ▼                       ▼
        ┌──────────┐          ┌──────────┐
        │ Binlog   │          │  Verify  │
        │ Replic.  │          │  Tool    │
        └──────────┘          └──────────┘
```

**3. 关键步骤（六个阶段）**

**阶段一：数据全量同步**
- 使用工具（如阿里开源的 DTS、或者 Maxwell + Canal、或者 AWS DMS）从旧库导出全量数据，导入新库
- 加一个 checksum 验证步骤——全量数据导入完成后比对两边的数据量、checksum 是否一致
- 这个阶段不阻断业务，旧库正常读写

**阶段二：增量实时同步**
- 开启 Binlog 监听（Canal / Maxwell 监听 MySQL Binlog），将增量变更实时同步到新库
- 需要确保 Binlog 格式为 ROW 模式（Statement 模式不支持异构迁移）
- 监控同步延迟——目标是将延迟控制在 1 秒以内
- 这个阶段两个库是"双写"的：业务写旧库、通过 Binlog 同步到新库

**阶段三：数据校验 + 补偿**
- 运行数据一致性校验工具（如 pt-table-checksum），逐表比对两边的数据
- 对于不一致的数据，根据 Binlog 重新同步（增量补偿）
- 重复验证直到两边数据完全一致，且延迟在可接受范围（< 1 秒）

**阶段四：灰度切换读流量**
- 在应用层通过配置中心切换读流量：先切 1% 的读请求到新库，观察延迟和错误率
- 逐步扩大到 10% -> 50% -> 100%
- 如果发现新库性能不如预期，回滚读流量到旧库（不需要写回滚，因为写还在旧库）

**阶段五：切换写流量（关键步骤）**
- 这是风险最高的步骤。做法是在一个业务低峰期，暂停旧库的写入（或通过 DTS 做双向同步）
- 将写流量切换到新库
- 切换到新库后，让旧库变成新库的从库，继续接收增量数据（以防需要回滚）

**阶段六：收尾**
- 确认新库运行稳定（至少观察 1-2 个业务高峰周期）
- 将旧库降级或下线（如果是平滑迁移，旧库可以保留作为延迟备份）
- 更新连接配置和 DNS 记录

**4. 深度讨论**

**Q: 迁移过程中旧库的数据写入量很大，Binlog 同步跟不上了怎么办？**
A: 这是常见的坑。解决方案：1）提升新库的写入性能（调整参数如 innodb_buffer_pool_size、增加 IOPS）；2）开启 Binlog 并行复制（MySQL 5.7+ 支持基于 database 的并行复制，8.0 支持基于 log 的并行复制）；3）如果仍然跟不上，需要做"灰度迁移"——按业务域分批迁移，而不是一次性迁移全部库表。

**Q: 切换写流量时如果出现问题怎么回滚？**
A: 这就是为什么阶段五中要让旧库保持为从库——如果新库有问题，只需要在应用层把写流量切回旧库，旧库的数据是完整且最新的。如果旧库已经被完全切断了，回滚就会非常痛苦。

**Q: 有没有不需要双写的方案？**
A: 有。如果目标数据库和源数据库兼容（如 MySQL -> MySQL 同构迁移），可以使用 Proxy 层（如 ProxySQL、MyCat）做透明迁移。Proxy 层可以根据路由规则将读写流量分流到新旧集群。这样做的好处是应用层不需要感知迁移过程。

## Q4: 设计一个事故响应系统（Incident Response System）

**难度**: ⚫⚫⚪ 中级 | **面试公司**: 字节跳动、腾讯、Meta

**问题原文**: "Design an incident response system." / "设计一个故障响应和处理流程系统。"

**回答**:

**1. 需求澄清**

- 目标：将"人找人"的混乱模式变成"系统驱动"的有序流程
- 需要覆盖：告警触发 -> 人员通知 -> 响应确认 -> 故障处理 -> 复盘改进
- 团队：50+ 微服务，20+ On-Call 工程师，分布在多个时区

**2. 整体设计**

```
            ┌──────────┐
            │  Alert    │
            │  Sources  │
            │ (Prom/   │
            │  ES/    │
            │  Sentry) │
            └────┬─────┘
                 │
                 ▼
        ┌────────────────┐
        │  Alert Router   │
        │  + Deduplication│
        │  + Correlation  │
        └──────┬─────────┘
               │
        ┌──────┴─────────┐
        │  On-Call        │
        │  Schedule       │
        │  (PagerDuty/    │
        │   OpsGenie)     │
        └──────┬─────────┘
               │
        ┌──────┴─────────┐
        │  Incident       │
        │  Management     │
        │  Platform       │
        │  (Statuspage/   │
        │   FireHydrant)  │
        └──────┬─────────┘
               │
        ┌──────┴─────────┐
        │  Postmortem     │
        │  + Action Items │
        └────────────────┘
```

**3. 关键设计决策**

**告警生命周期管理**：

告警不是直接通知人的，而是经过一个"处理管道"：
1. **Deduplication（去重）**：同一告警在 5 分钟内多次触发，只发送一次
2. **Grouping（分组）**：由同一根因导致的告警合并为一个 Incident（例如一个 K8s 节点宕机导致的 20 个 Pod 告警合并为一个 Node Failure Incident）
3. **Enrichment（补充信息）**：自动带上 Runbook 链接、相关 Dashboard 链接、最近变更记录
4. **Severity Classification（严重等级）**：
   - Sev0: 核心服务完全不可用，立即响应（15 分钟内确认）
   - Sev1: 部分功能受损或性能严重下降，快速响应（1 小时内确认）
   - Sev2: 非关键功能异常，正常工作时间响应
   - Sev3: 问询/告警，无需立即处理

**Incident Command System**：

当告警被确认并升级为 Incident 时，系统自动分配角色：
- **Incident Commander (IC)**：负责全局协调，不负责具体的排查操作。需要冷静、有条理、有决策力
- **Technical Lead**：负责技术排查和修复，通常由了解该服务的人担任
- **Communications Lead**：负责对内对外的状态更新，确保信息透明
- **Scribe**：记录时间线和操作日志——供事后复盘使用

**沟通渠道**：

- 每个 Incident 自动创建一个专属 Slack/DingTalk 频道
- 系统在频道内自动发送：告警详情、Runbook 链接、相关人员 roster
- IC 每 15 分钟在频道内发一次状态更新（即使还没有进展）
- 对内：团队成员在频道中获取信息；对外：通过 Statuspage 更新给用户

**事后复盘（Postmortem）**：

- 每一件 Sev0/Sev1 事故必须在 48 小时内完成复盘
- 复盘的输出是 Action Items，每个 Action Item 必须指定：负责人、截止日期、验证方式
- 复盘文档使用"无责备"（Blameless）原则——不追究个人责任，而是找到系统层面的改进空间
- 关键指标：Action Items 的完成率应该 >= 90%，未完成的 Action Items 需要在下次复盘中被继续追踪

**4. 深度讨论**

**Q: 如果值班的人正好在开会/不在线，怎么办？**
A: 设计 Escalation Policy——如果 Primary 在 5 分钟内未确认，自动通知 Secondary；再 5 分钟未响应，通知值班经理；再 5 分钟通知部门负责人。这个链要提前配置好，不要让 On-Call 人员在慌乱中手工联系。

**Q: 怎么度量 Incident Response 的效果？**
A: 三个指标：MTTA（Mean Time to Acknowledge，从告警发出到有人确认的时间）、MTTR（Mean Time to Resolve，从告警发出到恢复的时间）、以及 Action Items 完成率。

**Q: 怎么防止复盘流于形式？**
A: Action Items 需要有明确的验证方式。好的 Action Item 是"给 MySQL 的慢查询添加 P99 告警"，而不是"优化数据库性能"。同时，每次复盘的 Action Items 要在下一次复盘开始时 Review 完成情况。

## Q5: 设计云基础设施的成本优化方案

**难度**: ⚫⚫⚪ 中级 | **面试公司**: 字节跳动、阿里、快手

**问题原文**: "How do you design a cost optimization strategy for cloud infrastructure?" / "设计一个云成本优化方案。"

**回答**:

**1. 需求澄清**

- 云厂商：阿里云或 AWS
- 规模：1000+ 台 ECS/EC2，500+ 个 RDS 实例，混合使用预留实例和按量付费
- 目标：在不影响性能的前提下，降低 20-30% 的云支出
- 范围：只包含基础设施（IaaS/PaaS），不含 SaaS

**2. 优化维度**

成本优化不是"砍预算"，而是消除浪费和提高效率。我从四个维度入手：

**维度一：资源利用率优化（最大收益，最低风险）**

这是最优先做但最容易被忽略的。

- **识别"肥实例"**：很多团队为了"保险起见"，会申请远超实际需求的实例规格。通过分析过去 30 天的 CPU/内存/网络使用率，可以找到那些平均使用率低于 20% 的实例并降配。我见过一个典型的案例：一个 32C64G 的 Redis 实例，实际 CPU 使用率不到 5%，降配到 8C16G 后直接节省 75%
- **K8s 集群的 Request/Limit 优化**：使用 VPA（Vertical Pod Autoscaler）或自定义脚本分析 Pod 的实际资源消耗，给出 Request/Limit 的推荐值。平均优化 15-25% 的集群资源浪费
- **识别空闲资源**：深夜的开发和测试环境、周末不使用的 Staging 环境——通过自动化的 Schedule 策略在非工作时间停止非生产实例

**维度二：计费模式优化（长期收益）**

- **预留实例/节省计划**：对于 7x24 运行的生产实例，使用 1 年或 3 年的预留实例/节省计划。按量付费 vs 3 年预留的差价通常在 40-60%
- **Spot 实例**：对于可中断的 workoad（CI Runner、批处理任务、大数据计算），使用 Spot/抢占式实例，成本可以再降 60-80%
- **存储分层**：访问频率低的日志数据从 SSD 迁移到 HDD 或归档存储，冷数据（>90 天没访问过）自动转为 Glacier/归档存储

**维度三：架构优化（中高风险，高收益）**

- **弹性伸缩**：对于有波峰波谷的业务，使用 HPA 或 Cluster Autoscaler 代替固定副本数。特别是电商、游戏等有明显日周期和活动周期的业务
- **缓存策略**：在数据库前加一层 Redis/CDN，减少直接对数据库的查询。这个需要架构改造，但收益很大
- **服务合并**：对于流量极低的内部服务，考虑合并到已有实例或使用 Serverless（FaaS）——有时候一个微服务每小时的请求量不到 100 次，独立部署一辆"高铁"

**维度四：组织机制（长期保障）**

- **成本标签（Cost Tagging）**：所有资源强制打上团队/项目/环境的标签，否则自动清理。没有成本归属，就没有成本意识
- **成本看板**：每个团队能看到自己团队的云成本趋势图和同比/环比变化。我和很多团队合作的经验是——一旦他们能看到自己花的钱，自然就会关注起来
- **预算告警**：设置月度预算，当支出超过预算的 80% 时触发告警

**3. 预期效果**

根据过往经验，这套策略的预期效果：
- 识别闲置资源：立即节省 5-10%
- 资源降配优化：节省 10-15%
- 预留实例替换：节省 15-25%（按量转预留）
- Spot 实例使用：节省 30-50%（仅限可中断 workload）

综合下来，如果现状比较"随意"，第一轮优化通常可以降低 25-35% 的整体支出。

**4. 深度讨论**

**Q: 业务团队不愿意配合降配怎么办？**
A: 不做强制降配，而是给业务团队一个选择：要么接受 Resource Budget 约束并自主优化，要么超支的部分从团队的 Innovation Budget 里扣。效果比技术强制好得多。

**Q: FinOps 在企业中怎么落地？**
A: FinOps 的三个阶段：Inform（成本可视化）、Optimize（优化措施）、Operate（持续运营）。关键是走完整个闭环，而不是只做了前两步。

**Q: 成本优化会影响稳定性吗？**
A: 有这种风险。所以所有的优化必须遵循"先测量后执行"原则：任何降配操作前，先采集 7 天以上的真实使用率数据做决策依据。对核心生产系统，保持一定的裕量（buffer），不要优化到临界点。

## Q6: 设计一个多区域灾难恢复（Disaster Recovery）方案

**难度**: ⚫⚫⚫ 高级 | **面试公司**: 阿里、腾讯、AWS、Google

**问题原文**: "Design a multi-region disaster recovery solution." / "设计一个跨区域容灾方案。"

**回答**:

**1. 需求澄清**

- 应用：一个电商平台的核心交易链路（用户、订单、支付）
- 现状：部署在单区域（阿里云上海 region）
- 目标：RTO < 15 分钟，RPO < 5 分钟
- 预算：备机成本不超过主机的 50%
- 容灾级别：需要应对 region 级故障（不是只应对 AZ 级故障）

**2. 架构方案：Active-Passive vs Active-Active**

先做一个关键决策：选择 Active-Passive（冷备/热备）还是 Active-Active（双活）。

| 特性 | Active-Passive | Active-Active |
|------|---------------|---------------|
| RTO | 5-15 分钟 | 秒级 |
| RPO | &lt;5 分钟 | &lt;1 秒 |
| 成本 | 约 40-50% 主站 | 约 150-200% 主站 |
| 复杂度 | 中 | 高 |
| 适用 | 大多数场景 | 极端高可用场景 |

在面试中，我推荐选择 **Active-Passive Warm Standby**——它是大多数公司实际采用的方案，平衡了成本和 RTO/RPO。Active-Active 在面试中可以提到作为延申讨论。

**3. Active-Passive 方案设计**

```
                    ┌──────────────────┐
                    │  Global Load     │
                    │  Balancer (DNS)  │
                    │  (Cloudflare/    │
                    │   Alibaba DNS)   │
                    └────────┬─────────┘
                             │
                    ┌────────┴────────┐
                    │                 │
              ┌─────▼─────┐    ┌─────▼─────┐
              │  Region A  │    │  Region B  │
              │  (Primary) │    │  (Standby) │
              │            │    │            │
              │  ┌──────┐  │    │  ┌──────┐  │
              │  │ App  │  │    │  │ App  │  │
              │  │Cluster│ │    │  │Cluster│ │
              │  └──┬───┘  │    │  └──┬───┘  │
              │     │      │    │     │      │
              │  ┌──▼───┐  │    │  ┌──▼───┐  │
              │  │ DB   │  │    │  │ DB   │  │
              │  │(RW)  │◄─┼────┼──┤(RO)  │  │
              │  └──────┘  │    │  └──────┘  │
              └────────────┘    └────────────┘
```

**组件说明**：

**Global Load Balancer**：
- 使用 DNS 级别 GSLB（Cloudflare Traffic 或阿里云 DNS）
- 健康检查：每 10 秒探测主 region 的健康端点
- 故障切换：探测失败 3 次后自动将流量解析到备 region

**数据库层**：
- 主 region：数据库可读写（Read-Write）
- 备 region：数据库只读（Read-Only）
- 使用 DTS/Canal 做跨区域的主从同步
- 同步链路必须切换到独立的网络链路（专线或 VPN），不要经过公网
- 备 region 的数据库配置必须至少和主 region 一致

**应用层**：
- 备 region 的应用集群保持最小运行规模（通常是主 region 的 30-40%），能支撑核心交易即可
- 备 region 的应用连接到备 region 的只读数据库，也可以预连接到主 region
- 关键：备 region 的应用代码版本必须和生产环境一致

**数据校验**：
- 跨 region 的数据同步需要持续的校验机制
- 每 15 分钟运行一次数据一致性检查
- 如果发现数据不一致，自动触发修复流程

**4. 切换流程**

当主 region 发生故障时，以下步骤需要写在 Runbook 中并定期演练：

```
Step 1: 确认故障（1 分钟）
  - 确认 GSLB 健康检查连续失败
  - 确认监控系统确认 region 不可用

Step 2: 切换 DNS（2 分钟 - DNS TTL + propagation）
  - 将 DNS 解析切换到备 region
  - 如果使用 Traffic Director 等流量调度工具，修改权重

Step 3: 提升备 region 数据库（1 分钟）
  - 将备 region 数据库从 Read-Only 提升为 Read-Write
  - 停止主从同步（防止网络恢复后数据冲突）

Step 4: 扩容备 region 应用（5 分钟）
  - 将备 region 的应用集群扩容到全量规模
  - 受限于备 region 的资源池，需要提前准备好 HPA 策略和资源配额

Step 5: 验证（1 分钟）
  - 确认核心接口返回正常
  - 确认数据库写入正常
  - 通知业务方：切换完成

总时间: ~10 分钟（满足 RTO < 15 分钟）
```

**5. 深度讨论**

**Q: 双活（Active-Active）方案怎么做？**
A: 双活要求两个 region 同时处理读写流量。最大的挑战是数据冲突——同一个用户的同一条数据在两个 region 同时被修改怎么办。解决方案通常结合三种手段：1）数据分片（User ID 哈希按 region 分片，每个 region 只负责一部分用户）；2）冲突解决策略（最后写入者胜出 LWW、CRDT、或者人工仲裁）；3）业务层改造（比如"一个用户的所有请求路由到同一 region"）。

**Q: 怎么确保容灾方案真的有效？**
A: 定期演练。容灾方案的最大陷阱是"从来没切过"——你永远不知道哪里会出问题直到你真的切了。建议每季度至少做一次完整的切换演练，每半年做一次"出其不意"的演练（不通知团队具体时间）。演练发现的问题要像生产故障一样复盘和改进。

**Q: 跨 region 的网络延迟怎么处理？**
A: 中国国内 region 间延迟通常在 20-30ms，可以接受。国际 region 延迟可能 100-200ms，这时候需要：1）使用全球加速（如 AWS Global Accelerator）；2）将需要跨 region 访问的数据用 CDN 缓存或本地缓存；3）考虑业务拆分为独立的 regional 实例。

## Q7: 设计一个容器编排平台

**难度**: ⚫⚫⚫ 高级 | **面试公司**: 字节跳动、阿里、腾讯、Uber

**问题原文**: "How would you design a container orchestration platform?" / "设计一个容器编排平台，假设你不能直接用 K8s。"

**回答**:

**1. 需求澄清**

面试官问这个问题通常有两种意图：1）考察你对 K8s 设计原理的理解深度（即使你不能直接用 K8s，你的设计应该会接近 K8s 的架构）；2）或者他们确实在做 K8s 之上的调度增强。

- 规模：5000+ 节点，50000+ 容器
- 部署方式：混合部署在线服务和离线任务
- 需求：资源利用率要高（目标 40%+），支持多种工作负载类型

**2. 整体架构**

```
┌─────────────────────────────────────┐
│         Control Plane               │
├─────────────────────────────────────┤
│  API Server     │   Scheduler       │
│  (REST API +    │   (调度策略引擎)    │
│   Auth)         │                   │
├─────────────────┼───────────────────┤
│  Controller     │   etcd (状态存储)  │
│  Manager        │                   │
│  (Reconciler)   │                   │
└────────┬────────┴────────┬──────────┘
         │                 │
         ▼                 ▼
┌─────────────────────────────────────┐
│         Data Plane                  │
├─────────────────────────────────────┤
│  ┌─────────────┐ ┌─────────────┐  │
│  │  Node Agent  │ │  Runtime    │  │
│  │  (健康汇报、  │ │  (containerd│  │
│  │   指令执行)   │ │   /runc)   │  │
│  └─────────────┘ └─────────────┘  │
│  ┌─────────────┐ ┌─────────────┐  │
│  │  CNI Plugin  │ │  CSI Plugin │  │
│  │  (网络)      │ │  (存储)     │  │
│  └─────────────┘ └─────────────┘  │
└─────────────────────────────────────┘
```

**3. 关键设计决策**

**API Server**：
- 中心化的 API 入口，所有组件的操作都通过 API Server
- 使用声明式 API（Declarative API）而非命令式——用户提交"期望状态"，系统负责达到该状态
- 状态存储在 etcd（分布式一致键值存储），etcd 使用 Raft 协议保障一致性
- 认证和授权：使用 RBAC + OIDC

**Scheduler**：
- 调度不是简单的"找一个有足够资源的节点"，而是多维度打分：
  - 资源维度：CPU、内存、GPU、网络带宽
  - 亲和性维度：同一服务的 Pod 分散到不同节点（反亲和）、需要访问同一数据的 Pod 尽量放在同节点（亲和）
  - 拓扑维度：流量优先的 Pod 放在同一机架以减少延迟
  - 碎片优化：剩余资源能够被后续任务匹配
- 调度策略可以是：Binpacking（提高资源利用）或 Spreading（提高可用性），按 workload 类型配置
- 对于在线服务，优先 Spread——一个节点故障不会影响太多实例
- 对于离线任务，优先 Binpacking——资源利用最大化

**Controller Manager**：
- 采用 Reconciliation Loop（调谐循环）模式：Controller 从 API Server Watch 资源状态，比较"当前状态"和"期望状态"，执行操作使两者一致
- 常见的 Controller：Deployment Controller（管理 Pod 副本数）、Node Controller（管理节点生命周期）、Namespace Controller

**Node Agent**：
- 每个节点上运行的 Agent，负责：上报节点健康状态和资源使用量、执行从 API Server 下发的容器操作指令、采集 Pod 指标并上报
- Agent 必须设计为"即使 API Server 不可达，已运行的容器不受影响"

**网络模型**：
- 每个 Pod 一个独立 IP，Pod 之间可以直接通信（不需要 NAT）
- 网络插件（CNI）负责 IP 分配和路由配置
- 支持 Service 抽象——一组 Pod 前面有一个稳定 VIP/DNS 名称，实现负载均衡

**4. 深度讨论**

**Q: 5000+ 节点规模，etcd 的瓶颈怎么处理？**
A: etcd 的瓶颈主要是 watch 连接数和写入吞吐。解决方案：1）etcd 集群独立部署到高性能节点（SSD、充足的 IOPS）；2）控制 watch 的数量——避免每个节点都 watch 所有资源；3）使用 etcd v3 的 Compact 和 Defrag 控制数据量大小；4）API Server 增加缓存层，减少对 etcd 的直接读请求。

**Q: 混合部署在线服务和离线任务，怎么防止离线任务影响在线服务？**
A: 使用两级隔离机制。第一级：CGroup 的资源隔离（CPU Share、Memory Limit、BlkIO Weight）。第二级：资源超卖控制——在线服务预留的资源不能被离线任务使用，但在线服务没用完的资源可以分配给离线任务，在线服务需要时立即抢占回来。这个机制在字节跳动的"Gangsch"调度和腾讯的"Crane"中都有实现。

**Q: 如果一个节点宕机了，你怎么保证上面的服务自动恢复？**
A: Controller 监测到节点心跳超时后，将节点状态标记为 Unknown，然后将该节点上的 Pod 调度到其他节点。关键是 Grace Period 的设置——太短会误判网络抖动，太长会导致恢复慢。通常设置为 30-60 秒。

## Q8: 设计一个日均 100TB 日志的采集和可观测性管道

**难度**: ⚫⚫⚫ 高级 | **面试公司**: 字节跳动、腾讯、阿里、Uber

**问题原文**: "Design a logging and observability pipeline for 100TB/day." / "设计一个日处理 100TB 日志的管道。"

**回答**:

**1. 需求澄清**

- 日志来源：5000+ 台机器、1000+ 微服务
- 数据量：日均 100TB（峰值可能是均值的 2-3 倍）
- 数据用途：故障排查、监控告警、安全审计、业务分析
- 保留需求：热数据 7 天，温数据 30 天，冷数据 1 年
- 查询需求：支持全文搜索、Label 过滤、聚合统计

**2. 整体架构**

```
Agent Layer          Buffer Layer          Processing Layer       Storage Layer
┌────────┐          ┌────────┐          ┌──────────────┐       ┌──────────┐
│FluentBit│────────►│ Kafka  │────────►│ Log Processor │──────►│ Hot: S3  │
│(DaemonSet)│       │ (12+   │          │ (Flink/       │       │ + Loki   │
│sidecar  │         │ 分区)  │          │  Spark)       │       ├──────────┤
│hostPath │         │        │          │               │       │ Warm: S3 │
└────────┘          └────────┘          │ - Parsing     │       │ + Parquet│
                                         │ - Indexing    │       ├──────────┤
                                         │ - Routing     │       │ Cold: S3 │
                                         │ - Filtering   │       │ Glacier  │
                                         └──────────────┘       └──────────┘
                                                                     │
                                                               ┌─────▼─────┐
                                                               │  Query    │
                                                               │  Engine   │
                                                               │  (Grafana │
                                                               │   Loki/   │
                                                               │   Trino)  │
                                                               └───────────┘
```

**3. 关键设计决策**

**采集层（Agent Layer）**：

使用 FluentBit 而非 FluentD。原因是 FluentBit 是用 C 编写的，内存占用极低（约 5MB/实例），而 FluentD 基于 Ruby，内存占用 50-100MB。对于 5000+ 节点，每个节点节省 50MB 就是 250GB 的总内存节省。

采集模式：每个节点一个 DaemonSet FluentBit，采集宿主机上的所有容器日志。对于需要特殊解析的服务，使用 sidecar 模式的 FluentBit。

Agent 的核心设计原则：采集 Agent 本身必须稳定，即使它挂了也不应该影响业务容器。

**缓冲层（Buffer Layer）**：

Kafka 是必须的。原因：日志采集是"生产者快于消费者"的典型场景。Kafka 作为缓冲层可以：
1. 解耦采集和处理的速度
2. 提供数据重放能力（如果下游处理失败，可以从 Kafka 重放）
3. 支持多个消费者（实时查询、离线分析、长期归档各一个 consumer group）

Kafka 的配置：分区数按吞吐量计算——每个分区约处理 10MB/s，100TB/天 ≈ 1.16GB/s，所以至少需要 120+ 分区。按 3 副本计算，存储需求约 300TB（含 3 天缓冲）。

**处理层（Processing Layer）**：

使用 Flink 或 Spark Streaming 做流式处理。每个日志记录的处理步骤：
1. **解析**：从原始文本中提取结构化的字段（时间戳、级别、服务名、traceId 等）
2. **增强**：加入集群、节点、Pod 等上下文信息
3. **路由**：根据日志来源和类型路由到不同的存储
4. **采样**：对于 DEBUG/INFO 级别的日志，按比例采样（如 10%）；ERROR/FATAL 的日志全量保留
5. **告警**：匹配告警规则后直接发送到告警系统

**存储层（Storage Layer）**：

存储按"热 -> 温 -> 冷"分层：

- **热存储（7 天）**：使用 Loki + 本地 SSD。Loki 的索引方式基于 Label 而不是全文倒排索引，存储效率比 Elasticsearch 高 3-5 倍。对于 100TB/天，如果使用 ES，即使压缩后也需要约 30TB/天存储，Loki 可以降到 10TB/天以下
- **温存储（30 天）**：数据以 Parquet 格式存储在 S3（列式存储，压缩率高，适合分析查询）。使用 Trino/Presto 作为查询引擎
- **冷存储（1 年）**：数据自动转换到 Glacier/归档存储。查询冷数据的响应时间是分钟级

**4. 深度讨论**

**Q: 为什么选 Loki 而不是 ES？**
A: 成本是首要考虑。ES 的倒排索引存储开销很大，对于 100TB/天的日志量，ES 集群可能需要几百台高配机器。Loki 的架构决定了它的存储成本是 ES 的 1/3 到 1/5。但 Loki 的查询能力不如 ES 灵活（不支持复杂的全文检索），如果需要 grep 式的日志搜索，Loki 更适合，如果需要 Splunk 式的高级搜索，ES 更合适。

**Q: 如何处理日志采集丢失的数据？**
A: 三层保障：1）FluentBit 有内存缓冲和文件缓冲（内存满了写到磁盘），防止 Agent 重启时丢数据；2）Kafka 的持久化保证数据不会因消费者失败而丢失；3）端到端的校验——在日志产生时和写入存储时分别统计日志量，比对差值发现异常。

**Q: 100TB/天的查询延迟怎么保证？**
A: 查询延迟是分层的。热数据查询 < 1 秒——Loki 的 Label 索引 + SSD 存储。温数据查询 < 10 秒——Parquet 列式存储的扫描效率很高。冷数据查询分钟级——需要从 Glacier 取回数据。关键是要在前端限制用户的查询范围（强制选择时间范围和 Label），避免全量扫描。

## Q9: 设计一个快速增长服务的容量规划方案

**难度**: ⚫⚫⚫ 高级 | **面试公司**: 字节跳动、拼多多、Meta

**问题原文**: "How do you approach capacity planning for a rapidly growing service?" / "服务流量半年增长 5 倍，你怎么规划容量？"

**回答**:

**1. 需求澄清**

- 服务：一个在线 API 服务，当前 QPS 10 万
- 增长预期：6 个月后 QPS 50 万
- 现状：部署在 100 台物理服务器/虚拟机，资源使用率约 40%
- 约束：不能接受因为容量不足导致的限流或降级

**2. 方法论框架**

容量规划不是"预测未来然后买机器"，而是一个持续循环的过程：测量 -> 建模 -> 规划 -> 验证。

**Step 1: 建立基准线（Baseline）**

先搞清楚当前系统的容量上限在哪里。

- **压力测试**：对每个核心服务做压力测试，找到以下阈值：
  - CPU 使用率多少时 P99 延迟开始上升
  - 内存使用率超过多少时 GC 频率急剧增加
  - 数据库连接数达到多少时查询延迟开始劣化
  - 网络带宽打满时丢包率多少
- **关键指标**：每个服务当前的"最大承载能力"（例如：单实例 QPS 上限、单数据库连接池最大连接数等）

结果是一张表：

| 组件 | 当前容量 | 当前使用率 | 扩容步长 |
|------|---------|-----------|---------|
| API Server (单台) | 2000 QPS | 50% (1000 QPS) | 加实例 |
| MySQL (主库) | 5000 QPS | 60% (3000 QPS) | 读写分离/分库 |
| Redis | 10万 QPS | 30% (3万 QPS) | 加分片 |
| Kafka | 50MB/s | 20% (10MB/s) | 加分区 |

**Step 2: 建立增长模型**

根据业务增长预期，换算成各个资源维度的需求增长：

```
当前 QPS 10 万 → 6 月后 50 万 = 5 倍增长
每台 API Server 支撑 2000 QPS
当前需要 100 台（40% 利用率），实际最大承载 250 台
5 个月后需要 50000万 / 2000 = 250 台
注意增长不是线性的，要考虑：
- 数据库连接数增长
- 缓存命中率变化（QPS 增加后缓存命中率可能下降）
- 写入量的增长速度可能不同于读
```

**Step 3: 制定容量计划**

容量计划不是"增加多少机器"，而是多个维度的方案：

**水平扩容（Horizontal Scaling）**：
- API 层最容易——加实例、调整 HPA 上限
- 关键约束是 IP 地址池、K8s Node 资源配额、LB 的连接数上限
- 需要提前申请资源配额（云厂商的资源不是无限供应的）

**数据库扩容**：
- 这是最常见的瓶颈。增长 5 倍 QPS 直接打到数据库时，数据库很可能扛不住
- 分层缓解：Redis 缓存命中率 > 95%（从 10 万 QPS 中拦截 9.5 万）、数据库只处理 0.5 万
- 如果缓存命中率下降，需要提前加 Redis 分片
- 数据库层面考虑读写分离，主库扛写入、从库扛读

**第三方依赖**：
- 如果服务依赖外部 API（支付、短信、地图等），这些第三方也有容量上限
- 需要提前通知第三方，确认他们的服务能支持增长

**Step 4: 自动化验证**

容量规划不能靠"手工计算 + 祈祷"。需要建立自动化验证机制：

- **自动扩缩容测试**：定期通过流量回放对系统进行满负荷测试，验证自动扩容策略的实际效果
- **压测门禁**：每个新版本上线前，必须经过与生产流量等量的压力测试，确保性能没有退化
- **实时容量看板**：每个服务在 Dashboard 上显示当前使用率和剩余容量，接近阈值时自动告警

**3. 实际案例**

我经历过一个类似的 case：某电商服务的 QPS 在双十一期间增长了 8 倍。容量规划过程中的几个关键发现：

1. **数据库连接数是隐藏瓶颈**。增加 API 实例会线性增加数据库连接数。当连接数超过 2000 后，MySQL 的线程调度开销急剧上升。解决方案是加了一层连接池代理（ProxySQL 或 RDS Proxy）
2. **监控系统本身也需要扩容**。QPS 翻 5 倍意味着监控指标数量也翻 5 倍。如果不提前扩容 Prometheus，第一个挂的可能是监控系统
3. **最重要的是"Buffer"**。好的容量规划不是刚刚好够用，而是留出 30-50% 的 buffer 应对突发流量和异常情况

**4. 深度讨论**

**Q: 如果实际增长超过预期怎么办？**
A: 设计"三天扩容"的目标——在任何时候，如果需要扩容资源，从申请到上线不超过 3 天。这需要：1）资源配额提前申请好；2）扩容流程完全自动化（不要在扩容时卡在人工审批）；3）和云厂商有快速响应的通道。

**Q: 怎么判断是"真的需要扩容"还是"代码有性能问题"？**
A: 在扩容之前，先做一次性能优化。我见过太多例子——加机器解决不了代码层面的性能问题。建议顺序是：Profiling -> 优化代码 -> 缩容验证 -> 确认确实是容量不足了再扩容。

**Q: 容量规划和成本控制怎么平衡？**
A: 这是"有备无患"和"不浪费"之间的权衡。我给出的方案是：核心链路过量供应（buffer 50%），非核心链路按需供应（buffer 20%），离线任务弹性供应（buffer 0% 到 100% 用 Spot 实例）。

## Q10: 设计一个 secrets 管理系统

**难度**: ⚫⚫⚪ 中级 | **面试公司**: 阿里、字节跳动、腾讯

**问题原文**: "Design a secrets management system." / "设计一个密钥/凭据管理系统。"

**回答**:

**1. 需求澄清**

- 需要管理的 secrets 类型：数据库密码、API Token、SSH 密钥、TLS 证书、第三方服务的 Access Key
- 规模：管理 10000+ 个 secrets，服务 500+ 微服务
- 环境：混合云（自建机房 + 公有云）
- 安全要求：所有 secrets 在传输和存储时必须加密，必须支持审计日志
- 运维要求：secrets 的轮换必须自动化，不能依赖人工操作

**2. 整体架构**

```
┌──────────────────────────────────────┐
│          Secrets Store               │
├──────────────────────────────────────┤
│  ┌────────┐  ┌────────┐  ┌────────┐ │
│  │  Vault  │  │  AWS   │  │  K8s   │ │
│  │ Server  │  │ Secrets│  │ Secrets│ │
│  │ (Hashi) │  │ Manager│  │ (ESO)  │ │
│  └────▲───┘  └────────┘  └────────┘ │
│       │                              │
│  ┌────┴───┐                          │
│  │  Audit  │                         │
│  │  Log    │                         │
│  └────────┘                          │
└──────────────────────────────────────┘
       │
       │ 加密传输 (TLS + mTLS)
       │
┌──────┴──────────────────────────────┐
│          Client Side                │
├─────────────────────────────────────┤
│  ┌──────────┐  ┌──────────────────┐ │
│  │ App Code  │  │ Sidecar/Init    │ │
│  │ (Runtime  │  │ Container       │ │
│  │  Fetch)   │  │ (Inject Env)    │ │
│  └──────────┘  └──────────────────┘ │
└─────────────────────────────────────┘
```

**3. 方案选择**

生产环境我推荐使用 HashiCorp Vault + External Secrets Operator（K8s 场景），而不是自研。原因是 secrets 管理涉及到密码学、硬件安全模块（HSM）、审计合规等专业领域，不是 DevOps 团队应该自研的。

**4. 关键设计**

**存储模型**：

Secrets 存储在 Vault 中，以路径（Path）组织：

```
secret/
├── database/
│   ├── prod/
│   │   ├── user-service
│   │   └── order-service
│   └── staging/
│       └── ...
├── api-tokens/
│   ├── payment-gateway
│   └── sms-service
└── tls/
    ├── api.example.com
    └── ...
```

每个 secret 有版本号，支持版本回滚。历史版本不可删除（审计要求）。

**访问控制**：

- 使用 Vault 的 Policy 机制：每个服务只能访问自己路径下的 secrets
- 策略最小化原则：只给服务需要的 secrets 的读权限，不给写权限
- 写权限只给 CI/CD 系统和管理员

```
# 示例 Policy
path "secret/database/prod/user-service" {
  capabilities = ["read", "list"]
}
```

**身份认证**：

- 在 K8s 中，使用 Vault Agent Sidecar Injector——Pod 启动时自动注入一个 sidecar，通过 K8s ServiceAccount Token 向 Vault 认证
- 在虚拟机场景，使用 AppRole——每个应用有一个 RoleID 和 SecretID，Vault 返回一个短期 Token
- 所有 Token 都有 TTL（默认 24 小时），到期后需要重新获取

**Secrets 轮换**：

- 静态 secrets（如数据库密码）：Vault 支持自动轮换——配置轮换周期（如每 90 天自动更换密码）
- 动态 secrets（如数据库临时账号）：Vault 可以按需生成临时凭证——每次应用启动时获取一个有效期 24 小时的数据库账号，到期自动失效
- 动态 secrets 比静态 secrets 更安全——即使 Token 泄露，有效期有限

**审计日志**：

- 所有对 secrets 的访问、创建、修改、删除都必须记录审计日志
- 审计日志包含：谁（哪个服务/人）、在什么时间、访问了哪个 secret、操作类型
- 审计日志不可篡改（写日志的存储只有追加权限，没有修改权限）

**5. 深度讨论**

**Q: 如果 Vault 本身宕机了，所有服务都拿不到 secrets 怎么办？**
A: 这是一个关键问题。解决方案：1）Vault 集群高可用部署（至少 3 节点 + 自动故障转移）；2）本地缓存——sidecar 获取到 secret 后在内存缓存一份，即使 Vault 不可用，应用还能继续使用缓存的 secret（直到缓存 TTL 过期）；3）紧急访问流程——预先生成一批紧急备份 secret，存放在加密的离线存储中，Vault 不可用时手动激活。

**Q: 怎么把已有的 secrets 迁移到 Vault 中？**
A: 分阶段迁移。第一阶段：Vault 和现有 secrets 并行运行，新服务直接使用 Vault；第二阶段：对现有服务按优先级逐个迁移到 Vault；第三阶段：完全下线旧的 secrets 存储方式。不要在迁移过程中做"统一迁移"——风险太高。

**Q: GitOps 场景下，K8s Secrets 怎么管理？**
A: 绝对不要将 secrets 明文存储在 Git 仓库中（即使是私有仓库）。推荐方案：1）使用 External Secrets Operator（ESO）——在 Git 仓库中存储的是对 Vault 中 secret 的引用，ESO 负责从 Vault 同步到 K8s Secrets；2）使用 Sealed Secrets——用公钥加密后存储在 Git 中，集群内的 Controller 用私钥解密。ESO 更推荐，因为不需要管理密钥的密钥。
