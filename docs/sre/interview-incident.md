# 故障管理面试题

## Q1: 故障严重级别（Severity Level）如何定义和划分？P0 到 P3 各代表什么？

**Difficulty**: ⚫⚪⚪ Junior | **Companies**: 字节跳动、腾讯、阿里

**Key Points**:
- 故障级别根据影响范围（用户数/交易量）和影响程度（功能完全不可用/部分受损）划分
- P0（Critical）：核心功能完全不可用，影响所有用户
- P1（Major）：核心功能受损或部分用户不可用
- P2（Minor）：非核心功能受损，用户可以有绕行方案
- P3（Trivial）：轻微问题，不影响用户正常使用
- 级别定义需要在每个团队达成共识并且文档化

**Full Answer**:

故障级别的定义直接决定了"谁被叫醒"、"多长时间内响应"、"需要什么级别的资源介入"。每个公司有不同的叫法（Sev1-Sev4、P0-P3），但核心逻辑一致。

**通用的故障级别定义**：

```
P0 — 完全不可用（Total Outage）
  
  定义：核心服务对所有用户完全不可用，或直接影响收入的链路断裂
  
  判断标准：
  - 核心 API 错误率 > 50%
  - 首页/登录/支付完全不可用
  - 影响收入超过 100 万/小时
  - 核心数据丢失或泄露
  
  响应要求：
  - 确认时间：5 分钟内
  - 恢复目标：1 小时内
  - 通知范围：CTO/VP 级别
  - 响应模式：立即 War Room，全团队介入

P1 — 严重故障（Major Outage）
  
  定义：核心功能严重受损，或大量用户受到影响
  
  判断标准：
  - 核心功能错误率 > 10%
  - 非核心功能完全不可用
  - 影响 30% 以上的活跃用户
  - 重要第三方依赖中断超过 15 分钟
  
  响应要求：
  - 确认时间：15 分钟内
  - 恢复目标：4 小时内
  - 通知范围：部门负责人
  - 响应模式：值班工程师 + 相关团队

P2 — 一般故障（Minor Outage）
  
  定义：非核心功能异常，或有临时绕行方案
  
  判断标准：
  - 非核心功能部分受损
  - 影响 < 5% 的用户
  - 有合理的业务绕行方案
  - 性能下降但可用
  
  响应要求：
  - 确认时间：1 小时内
  - 恢复目标：8 小时内
  - 通知范围：团队内
  - 响应模式：工作时间处理

P3 — 轻微问题（Cosmetic Issue）
  
  定义：功能可用但体验不完美
  
  判断标准：
  - UI 显示问题
  - 非关键路径上的错误日志
  - 文档或配置错误
  - 需要改进但不紧急
  
  响应要求：
  - 确认时间：4 小时内
  - 恢复目标：24 小时内或下个迭代
  - 通知范围：不需要 On-call 通知
  - 响应模式：排入需求队列
```

**级别的动态调整**：

故障级别不是静态的——在故障处理过程中可能需要升降级：

```
升级条件：
  - P2 故障 2 小时内未解决 → 自动升级为 P1
  - P1 的影响面在扩大（如从 10% 扩展到 50%）→ 自动升级为 P0
  - 发现故障涉及数据丢失或安全漏洞 → 至少升级一级

降级条件：
  - 已找到绕行方案，用户影响大幅降低 → 可以降级
  - 确认影响范围小于最初评估 → 可以降级
```

级别变化的决策应该在 Incident Commander 或值班经理做出，并在沟通渠道中公告。

**常见误区**：

1. **把 P2 当 P0 告警**：每收到任何错误日志就拉 P0 War Room，导致"狼来了"效应
2. **把 P0 当 P2 处理**：核心支付故障还在缓慢排查，没有及时拉人——这是对故障严重性认识不足
3. **级别定义过于模糊**："严重影响用户体验"——什么叫"严重"？不如量化：错误率 > 10%、延迟 > 3s

**Follow-up Questions**:
- Q: 故障级别的定义应该由谁来审批？SRE 团队一个人说了算还是需要产品/业务方共同确认？
- Q: 夜间和节假日发生的 P2 故障是否需要叫醒 On-call 工程师？什么条件下 P2 在非工作时间可以不处理？
- Q: 如果客户通过客服渠道反馈的问题远多于监控发现的告警，这说明故障级别定义有问题还是监控覆盖不足？

## Q2: 事故指挥系统（Incident Command System, ICS）在故障处理中如何运作？各个角色的职责是什么？

**Difficulty**: ⚫⚫⚪ Intermediate | **Companies**: 字节跳动、阿里、腾讯

**Key Points**:
- ICS 源自消防/应急管理领域，被 Google, PagerDuty 等公司引入 IT 故障管理
- 核心原则：一个指挥、明确分工、避免"所有人都在排查但没人做决策"
- 关键角色：Incident Commander（IC）、Operations Lead、Communication Lead、Scribe
- IC 不参与具体排查——IC 的任务是协调、资源调度和决策
- 故障处理中最大的浪费是"10 个人都在看同一个日志但没人通知管理层"

**Full Answer**:

故障发生后最常见的错误是"所有工程师涌入同一个 Slack 频道，每个人都在做自己的猜测和排查，但没有人协调"。ICS 就是解决这个问题的。

**ICS 角色定义**：

```
Incident Commander（事故指挥官）
  ├─ 职责：不参与具体技术工作，专注于协调和决策
  ├─ 决定：是否需要升级、是否需要拉更多团队、对外沟通的时机
  ├─ 确保：有人在做关键动作、有记录、有人在对外沟通
  └─ 权力：可以调动任何需要的资源

Operations Lead（执行负责人）
  ├─ 职责：带领工程师进行技术排查和修复
  ├─ 汇报：向 IC 汇报当前诊断状态和方案
  └─ 注意：不要同时做 IC 和执行——否则没人协调

Communication Lead（沟通负责人）
  ├─ 职责：所有对外沟通的单一输出口
  ├─ 内部：向 IC 汇报故障状态
  ├─ 外部：向管理层、业务方、客户发布故障公告
  └─ 原则：即使是"还在排查"也要定期更新，不要沉默

Scribe（记录员）
  ├─ 职责：记录故障时间线——什么时间做了什么、谁做的
  └─ 产出：故障复盘的基础材料
```

**ICS 的运作流程**：

```
故障被确认（告警或用户反馈）
    │
    ▼
第一时间响应者成为"初始 IC"
  ├─ 评估故障级别，拉入相关人员
  ├─ 创建故障频道（Slack/飞书）
  ├─ 发布初始故障通告
  └─ 开始记录时间线
        │
        ▼
人员到位后，进行角色分配
  ├─ 如果 IC 需要参与技术排查 → 交接 IC 给其他人
  ├─ 指派 Operations Lead 负责技术
  ├─ 指派 Communication Lead 负责对外
  └─ 指派 Scribe
        │
        ▼
故障处理循环
  ├─ Operations Lead 定期向 IC 汇报状态（每 15-30 分钟）
  ├─ IC 决定是否需要更多资源、是否升级
  ├─ Communication Lead 周期性更新管理层
  └─ Scribe 持续记录
        │
        ▼
故障恢复
  ├─ 确认服务已恢复（不仅仅是"看起来好了"）
  ├─ 发布最终故障通告
  ├─ 解除 War Room
  └─ 安排复盘时间（24-48 小时内）
```

**ICS 的关键原则**：

1. **一个声音对外**：所有对外沟通（包括向 VP 的汇报）必须通过 Communication Lead。不允许工程师直接在管理层群里汇报情况——会导致信息混乱。

2. **IC 不碰键盘**：IC 绝对不能参与 debug。如果 IC 发现自己忍不住要看代码，说明需要交接角色给其他人。

3. **状态同步的节奏**：
   ```
   恢复前：IC 每 15 分钟向全员同步一次（不一定是新进展，可以是"仍在排查中"）
   恢复后：IC 每 30 分钟向管理层同步一次
   ```

4. **角色交接的仪式**：IC 交接时必须在频道中明确声明："I'm handing over IC to Alice. Alice, please confirm." Alice 回复确认。这样可以避免"我以为你在指挥"的歧义。

**Follow-up Questions**:
- Q: 小型故障（P2/P3）也需要完整的 ICS 流程吗？如何简化流程以适应不同级别的故障？
- Q: 如果 IC 在故障解决过程中做出了错误的决策（如决定不扩容），复盘时应该如何对待这个决策？
- Q: 如何培养 IC 角色？后备 IC 的梯队建设怎么做？

## Q3: 什么是"无责复盘"（Blameless Postmortem）？如何在复盘中发现系统性问题而不是追究个人责任？

**Difficulty**: ⚫⚫⚪ Intermediate | **Companies**: 阿里、字节跳动、腾讯

**Key Points**:
- 无责复盘的核心假设：人是善意的、有能力的，故障的根本原因是系统设计缺陷
- 复盘的目标是找出"系统为什么没有阻止人犯错"，而不是"谁犯了错"
- 通过"5 Whys"分析法追溯到系统性问题而不是个人行为
- 无责复盘的输出是"行动项"（Action Items），而不是"处分"（Accountability measures）
- 建立无责复盘文化需要管理层明确倡导并以身作则

**Full Answer**:

"Blameless"是 SRE 文化中最容易被误解的概念。无责复盘不是"不追究责任"——而是"追究的是系统责任而不是个人责任"。

**有责复盘 vs 无责复盘**：

```
有责复盘（Blame Culture）：
  问题：为什么线上执行了 rm -rf /data？
  结论：操作人员粗心大意，违反了操作规范
  行动项：对该员工进行绩效扣分，要求加强培训

无责复盘（Blameless Culture）：
  问题：为什么线上执行了 rm -rf /data？
  结论：1. 该环境没有权限分级——任何人都可以对/data 执行 rm
         2. 没有预检机制——高危命令没有二次确认
         3. 没有变更审批流程——任何命令都可以直接执行
  行动项：1. 实施权限分级，高危操作需要 sudo
          2. 所有 rm 命令增加 --preserve-root 和二次确认
          3. 建立变更管理流程
```

两者的核心差异：有责复盘认为"人出错了所以系统出错了"，无责复盘认为"系统设计没有考虑到人会出错，所以系统出错了"。

**5 Whys 分析法**：

```
问题：支付服务 P0 故障，用户无法支付 30 分钟

Why 1: 为什么支付不可用？
  因为支付服务的数据库连接池满了。

Why 2: 为什么数据库连接池满了？
  因为上游订单服务发了大量慢查询。

Why 3: 为什么订单服务会发慢查询？
  因为新发布的功能中，查询订单列表没有加 LIMIT。

Why 4: 为什么这个变更没有被测试发现？
  因为测试环境的数据量只有 100 条，而生产环境有 100 万条。

Why 5: 为什么测试环境的数据量和生产环境差距这么大？
  因为测试数据生成脚本没有更新，且没有"生产数据脱敏后导入测试环境"的流程。
```

5 Whys 的终点是"系统/流程/文化"层面的问题，而不是"人"的问题。在上面的例子中：
- 终点应该是"测试数据管理流程缺失"
- 而不是"开发人员没有测试大数据量场景"

**无责复盘模板**：

```markdown
# 故障复盘报告

## 基本信息
- 故障编号: INC-20260516-001
- 故障级别: P1
- 发生时间: 2026-05-16 14:00 - 14:45
- 影响范围: 支付模块 15% 用户超时
- 处理人: Alice (IC), Bob (Ops), Charlie (Comm)

## 故障描述
（简洁描述故障现象和影响）

## 时间线
| 时间 | 事件 |
|------|------|
| 14:00 | PagerDuty 触发 HighErrorRate 告警 |
| 14:03 | Alice 确认告警，创建 #incident-xxx 频道 |
| 14:05 | 确定影响面：支付超时，错误率 30% |
| ... | ... |
| 14:45 | 扩容数据库连接池后，错误率回到基线 |

## 根因分析（5 Whys）
...

## 直接原因
（技术层面：如"连接池配置错误"）

## 根本原因
（系统层面：如"没有连接池监控"、"扩容流程没有文档化"）

## 行动项
| 编号 | 行动项 | 类型 | 负责人 | 截止日期 | 状态 |
|------|--------|------|--------|----------|------|
| 1 | 增加数据库连接池使用率监控 | 监控 | Alice | 2026-05-23 | 进行中 |
| 2 | 建立测试环境数据量接近生产的流程 | 流程 | Bob | 2026-06-01 | 待开始 |
| 3 | All hands 分享本次复盘教训 | 文化 | Charlie | 2026-05-20 | 待开始 |
```

**无责复盘的文化建设**：

- 复盘会议只讨论"系统和流程"的问题，不讨论"谁提交了那行代码"
- 复盘报告提交前全员确认"这个报告可以用来辩护——如果有人起诉我们，这份报告不会成为辩护的不利证据。如果会，说明它仍然在追究个人责任。"
- 管理层在复盘会上做总结："这次故障没有任何一个人会被问责。我们要解决的是系统问题，不是追究谁。"
- 即使故障是由个人错误直接导致的（如误删），也应该追问为什么系统允许这样操作发生

**Follow-up Questions**:
- Q: 如果同一个工程师在 3 个月内犯了两次同样的错误，无责复盘还能适用吗？重复错误的边界在哪里？
- Q: 无责复盘和 Accountability（问责）之间如何平衡？完全不问责是否会降低团队的"责任意识"？
- Q: 无责复盘在金融、医疗等受监管行业如何落地？监管要求"查明责任人"和无责原则是否冲突？

## Q4: MTTR、MTBF 和 MTTD 这三个指标分别衡量什么？如何系统性地降低 MTTR？

**Difficulty**: ⚫⚫⚪ Intermediate | **Companies**: 腾讯、字节跳动、阿里

**Key Points**:
- MTTR（Mean Time to Resolve）：平均修复时间——从确认故障到恢复的时间
- MTBF（Mean Time Between Failures）：平均故障间隔——系统正常运行的平均时长
- MTTD（Mean Time to Detect）：平均发现时间——从故障发生到被检测到的时间
- 降低 MTTR 是 SRE 最核心的日常目标——比追求 MTBF 更有现实意义
- MTTR 的组成：MTTD + 诊断时间 + 修复时间 + 验证时间

**Full Answer**:

这三个指标从不同角度衡量系统的可靠性和团队的故障处理能力。面试中需要展示的不仅是定义，还有如何用这些指标来指导改进。

**三个指标的详细定义**：

```
MTTD（Mean Time to Detect）：故障发现速度
  ├─ 衡量：监控和告警系统的有效性
  ├─ 理想值：< 1 分钟（自动化告警），< 5 分钟（用户反馈）
  └─ 优化方向：监控覆盖度、告警灵敏度、告警到达路径

MTTR（Mean Time to Resolve）：故障恢复速度
  ├─ 衡量：整个故障处理流程的效率
  ├─ 理想值：P0 < 1h, P1 < 4h, P2 < 8h
  └─ 优化方向：自动化修复、Runbook 质量、值班工程师经验

MTBF（Mean Time Between Failures）：系统稳定性
  ├─ 衡量：系统设计是否健壮
  ├─ 理想值：越高越好（取决于服务关键程度）
  └─ 优化方向：架构改进、消除单点依赖、混沌工程
```

**MTTR 的分解**：

MTTR 不是单一的时间段，而是由多个阶段组成的：

```
故障发生    被检测到      开始诊断        定位根因        修复完成      验证通过
  │            │            │              │              │            │
  ▼            ▼            ▼              ▼              ▼            ▼
  ├── MTTD ──► ├── 诊断时间 ─►├── 修复时间 ─►├── 验证时间 ─►│
  │                                                                   │
  └──────────────────── MTTR ────────────────────────────────────────┘
```

**降低 MTTR 的具体策略**：

**1. 降低 MTTD：让告警更快、更准**
```yaml
# 不要在"日志级别"上告警，在"SLO 烧蚀率"上告警
# 错误配置：日志中出现 ERROR 就告警 → 噪音太多
# 正确配置：
- alert: ErrorBudgetBurnRate
  expr: |
    sum(rate(http_requests_total{status=~"5.."}[1m]))
    /
    sum(rate(http_requests_total[1m])) > 0.01
  for: 1m
  # 1 分钟内错误率超过 1%，立即告警
```

自动化检测指标覆盖率：核心服务 100% 自动覆盖检测异常 -> 自动通知 On-call

**2. 降低诊断时间：标准化诊断流程**
```bash
# 标准化诊断脚本：一键获取所有关键信息
./diagnose.sh service-name

# 输出：
# 1. 最近 30 分钟的 QPS、延迟、错误率
# 2. 最近 10 分钟的 Pod 事件（重启、OOM）
# 3. 最近 5 分钟的 ERROR 日志
# 4. 外部依赖健康状态（数据库、缓存、MQ）
# 5. 变更历史（最近一次发布、配置变更时间）
```

**3. 降低修复时间：自动化修复**
```
对于已知模式的故障：
  - 数据库连接池满 → 自动扩容连接池
  - 磁盘空间满 → 自动清理旧日志
  - CPU 飙高 → 自动扩容 Pod
  - 慢查询 → 自动 kill 长时间运行的查询

对于未知模式的故障：
  - 回滚最近的变更是最快的恢复手段
  - 保留最近 5 个版本的制品，随时准备回滚
```

**4. 降低验证时间：自愈验证**
```
修复完成后：
  - 自动运行健康检查（API 返回 200？）
  - 自动检查关键指标（错误率下降？延迟恢复正常？）
  - 自动对比恢复前后的指标基线
  - 验证通过后自动解除告警静默，关闭故障单
```

**MTTR 量化目标示例**：

```
服务级别      MTTD 目标    MTTR 目标     MTBF 目标
支付服务       < 1 分钟    < 15 分钟    > 30 天
订单服务       < 2 分钟    < 30 分钟    > 14 天
用户服务       < 5 分钟    < 1 小时     > 7 天
通知服务       < 15 分钟   < 4 小时     > 3 天
```

**Follow-up Questions**:
- Q: MTBF 到底有没有意义？MTBF 很高（服务长时间不故障）是否反而意味着 MTTR 的训练不够？
- Q: 如何避免"MTTR 指标驱动"导致的错误行为——为了缩短 MTTR 而重启服务而不是真正修复？指标引导的陷阱是什么？
- Q: 对于第三方依赖的故障（如云服务商宕机），MTTR 是如何计算的？不在控制范围内的故障时间是否应该计入？

## Q5: War Room（作战室）在故障处理中的最佳实践是什么？如何保证 War Room 高效运作而不混乱？

**Difficulty**: ⚫⚫⚪ Intermediate | **Companies**: 字节跳动、腾讯、阿里

**Key Points**:
- War Room 不是"所有人一起 debug"，而是"结构化协作"——指挥系统在物理场景中的体现
- 成功的 War Room 特征：单一沟通频道、明确的任务分配、固定节奏的状态同步
- 远程 War Room（Slack/飞书/Zoom）需要比物理 War Room 更严格的纪律
- War Room 需要明确的"停工条件"——什么时候停止，什么时候回归日常
- 避免"过度召集"——不是相关的人都应该进 War Room

**Full Answer**:

War Room 容易出现的两个极端：一是"群龙无首"——每个人都在说但没人协调；二是"人太多了"——故障频道里几百号人，噪音远大于信号。

**War Room 的启动条件**：

不是所有故障都需要 War Room。触发条件应该明确定义：

```yaml
# 满足以下任何一条，立即启动 War Room：
# 1. P0 故障确认
# 2. P1 故障超过 15 分钟未恢复
# 3. 影响面在持续扩大
# 4. 关键业务线的 VP 要求成立
# 5. 需要 3 个以上团队协作的故障
```

**物理 War Room 的准备**：

```
硬件：
  - 大屏幕（显示 Grafana 仪表盘、告警面板）
  - 独立的音频/视频设备
  - 计时器（显示故障持续时间）
  - 白板（记录关键信息和行动项）

软件：
  - 专用的故障频道（Slack/飞书），频道名包含故障编号
  - 共享文档（时间线记录、行动项追踪）
  - Zoom/Teams 会议室（远程参与）
  - 屏幕共享（只允许 IC 或 Operations Lead 共享）
```

**War Room 运作纪律**：

**沟通纪律**：
```
Do's:
  ✓ 每个发言前先说自己的角色："Operations Lead here..."
  ✓ 关键决策公开声明："I'm going to scale up the database pool to 200 connections"
  ✓ 定期状态同步（IC 每 15 分钟）
  
Don'ts:
  ✗ 不要在频道中闲聊或讨论无关话题
  ✗ 不要同时 ic 和操作——"I'm doing"和"IC here"是冲突的
  ✗ 不要私聊——所有故障相关信息必须在主频道中
```

**任务分配纪律**：
```
所有排查任务通过 IC 指派，格式：
  "Operations Lead, please investigate the database connection spike"
  "Alice, please check the last deployment time for payment-service"
  "Bob, prepare a rollback plan for version 3.2.1"

被指派者需要回复确认并定期更新状态：
  "Alice on it. [node], checking deployment history..."
  "Alice update: last deployment was 20 min ago. Investigating further..."
```

**信息记录纪律**：
```
时间线必须实时记录，格式：
  [14:00] PagerDuty triggered: HighErrorRate > 5%
  [14:03] Alice acknowledged, created #incident-123
  [14:05] IC assigned: Alice (initial)
  [14:08] Determined: payment service database pool exhausted
  [14:10] Operations Lead Bob scaled connection pool from 50 to 150
  [14:12] Error rate dropping... 
  [14:15] Error rate back to 0.1%, service recovered. IC declared resolved.
```

**War Room 的结束**：

```
故障恢复 ≠ War Room 结束

War Room 关闭条件（需全部满足）：
  ✓ 用户影响已消除（错误率、延迟恢复到基线）
  ✓ 核心监控指标已稳定 15 分钟以上
  ✓ 短期恢复措施已确认有效
  ✓ 已回滚有问题的变更或部署了修复版本

War Room 关闭后的工作：
  - IC 发布故障总结（Summary）
  - 通知管理层"故障已解决"
  - 创建复盘 Issue
  - 24-48 小时内安排复盘会议
  - 故障频道保留 7 天后归档
```

**远程 War Room 的特殊挑战**：

疫情时代后，远程 War Room 成为主流。它的挑战比物理 War Room 更大：
- 每个人多任务处理，注意力分散
- 缺少肢体语言和环境感知
- 网络延迟导致沟通不同步

应对方法：
- 更频繁的状态同步（每 10 分钟而不是 15 分钟）
- 强制所有人在 Zoom 中打开摄像头
- 使用"数字举手"机制来排队发言
- IC 需要更明确地点名："Alice, what's your status?"

**Follow-up Questions**:
- Q: War Room 中如果有多个团队的工程师在线，但没人听 IC 指挥怎么办？IC 的权威从哪里来？
- Q: 故障处理过程中，IC 发现自己的技术判断可能不对，应该如何纠正？在 War Room 中承认错误的文化如何建立？
- Q: 如何处理"故障疲劳"——团队经历了一次长时间（比如 8 小时）的 P0 故障后，人员身心俱疲，如何处理恢复后的状态？

## Q6: 故障沟通模板应该如何设计？对内、对外的故障通告分别应该包含哪些内容？

**Difficulty**: ⚫⚪⚪ Junior | **Companies**: 腾讯、字节跳动、阿里

**Key Points**:
- 故障沟通分为三个层次：内部技术同步、管理层汇报、用户/客户公告
- 内部沟通重点：影响面、当前行动、所需资源
- 管理层沟通重点：影响面、恢复 ETA、是否升级
- 对外沟通重点：歉意、受影响的服务、预期恢复时间、已采取的缓解措施
- 沟通的黄金法则："还有问题——但我们知道问题是什么——我们在解决"

**Full Answer**:

故障沟通的质量直接影响用户信任和管理层信心。一个写得好的故障通告可以安抚情绪、传递专业度；一个写得很差的通告会放大恐慌和不满。

**三层沟通模板**：

**第一层：内部技术频道（Slack/飞书）**

用于故障处理过程中的实时同步：

```
[INC-XXXX] 故障状态更新 @channel

级别: P0 | 持续: 32 分钟 | IC: Alice

当前状态:
- 影响: 支付服务 100% 失败，所有用户无法支付
- 根因: 数据库服务主库 CPU 100%，疑似慢查询导致
- 操作:
  - [X] 尝试 kill 慢查询
  - [ ] 扩容数据库（进行中）
  - [ ] 准备切流到从库

需要支持:
- 数据库 DBA 在线支持 —— DBA 到位了吗？
- 需要确认最近是否有 Schema 变更

下一次同步: 5 分钟后
```

**第二层：管理层同步（邮件/IM 私聊）**

用于向 VP、CTO 等管理层汇报：

```
主题: [故障通报] 支付服务 P0 故障 — 处理中

概要:
  支付服务自 14:00 起出现 100% 失败，所有用户无法完成支付。
  当前正在排查根因，预计恢复时间待定。

影响:
  - 所有交易中断（预计损失 X 万/小时）
  - 影响用户量: 约 10 万活跃用户
  - 波及服务: 订单、通知（依赖支付状态的链路）

处理进度:
  - 14:03 故障确认，启动 War Room
  - 14:10 定位到数据库 CPU 100%（疑似慢查询）
  - 14:15 开始 kill 慢查询进程
  - 14:20 数据库 CPU 下降到 60%，支付部分恢复
  - 14:30 全部恢复，监控指标正常

下一步:
  - 监控 15 分钟确认稳定性
  - 收集完整时间线
  - 安排复盘会议

预计下一轮更新: 15:00
```

**第三层：用户/客户公告（Status Page）**

对外公告的语言风格要温和、专业、有同理心：

```
[更新 14:45] 支付服务已恢复

我们检测到支付服务自北京时间 14:00 起出现服务中断，
原因是数据库系统异常导致请求超时。

在当前时间 14:45，服务已全面恢复。

处理过程：
  14:00 — 检测到支付失败率上升
  14:10 — 定位到根因（数据库慢查询）
  14:30 — 完成修复，支付恢复
  14:45 — 确认所有指标恢复正常

对您造成的不便，我们深表歉意。
我们将进行彻底的事后分析，并在 48 小时内发布复盘报告，
包括防止此类问题再次发生的改进措施。

如需获取最新状态，请关注 status.yourcompany.com。
```

**时间线驱动的沟通节奏**：

```
故障确认 → 5 分钟内发出初始通告
  "我们已注意到 XX 服务出现问题，正在排查中。"

根因发现 → 立即更新
  "已定位到根因：数据库慢查询导致连接池耗尽。正在修复。"

修复部署 → 立即更新
  "已部署修复方案（扩容连接池）。正在验证效果。"

服务恢复 → 5 分钟内发出恢复确认
  "服务已恢复正常。我们将在 48 小时内发布详细的复盘报告。"
```

**沟通的常见错误**：

1. **过度承诺 ETA**：没有确定根因时就说"预计 30 分钟恢复"——如果超过承诺时间会导致信任危机。正确说法："ETA 暂不确定，我们会每 15 分钟更新一次进度。"

2. **技术细节过多**：对外公告中出现 "CPU 100% caused by a full GC that blocked the connection pool" ——用户不关心 GC，只需要知道"支付正在恢复"。

3. **沉默**：故障处理中最好和最差的沟通区别在于：最好的沟通是"还在排查"——至少让人知道有人在处理。最差的沟通是 30 分钟没有消息。

4. **指责任何方**：在对外公告中绝对不能出现"第三方云服务商故障导致"、"上游团队的代码问题"——用户只关心你的服务是否可用。

**Follow-up Questions**:
- Q: 如果故障时间很长（如 8 小时），沟通频率和内容应该怎么变化？长时间故障中的沟通策略有什么不同？
- Q: 和客户成功团队（Customer Success）的同步机制如何设计？如何确保一线客服人员了解故障状态以便回答客户询问？
- Q: 故障恢复后的"道歉邮件"应该怎么写？是否需要提供补偿方案（如服务抵扣券）？由谁来批准？

## Q7: 故障复盘的流程是什么？如何确保复盘产生的行动项真正得到执行和跟踪？

**Difficulty**: ⚫⚫⚪ Intermediate | **Companies**: 阿里、字节跳动、腾讯

**Key Points**:
- 复盘不是"开会讨论"——它是结构化的流程：数据收集、分析、行动项、跟踪
- 复盘应该在故障恢复后 24-48 小时内进行——太早信息不全，太晚细节遗忘
- 行动项的 SLO：必须有明确的负责人、截止日期、验收标准
- 行动项跟踪比行动项定义更重要——没有跟踪的复盘毫无意义
- 行动项的比率目标：至少 80% 的行动项在下一次复盘前已完成

**Full Answer**:

很多团队的复盘做成了"开一个会、写一份报告、然后忘记它"。真正的复盘流程要求行动项的闭环跟踪。

**复盘的完整流程**：

```
第一步：数据收集（故障恢复后立即开始 ─ 恢复后 24 小时内）
  ├─ Scribe 整理时间线
  ├─ IC 补充关键决策点
  ├─ 收集所有相关人员的事件记录
  └─ 导出告警日志、监控图表（时间线对齐）
        │
        ▼
第二步：分析阶段（恢复后 24 小时内，分析者独立完成）
  ├─ 5 Whys 根因分析
  ├─ 识别直接原因和根本原因
  ├─ 识别"有利于恢复的因素"（做对了什么）
  ├─ 识别"阻碍恢复的因素"（可以做更好的）
  └─ 输出初步的复盘报告草案
        │
        ▼
第三步：复盘会议（恢复后 24-48 小时，45-60 分钟）
  ├─ 参与人员：IC、Operations Lead、相关工程师、TL
  ├─ 议程：
  │   1. 故障概述（5 分钟，由 IC 介绍）
  │   2. 时间线回顾（10 分钟，确认事实）
  │   3. 根因分析（15 分钟，聚焦"为什么"）
  │   4. 行动项讨论（15 分钟，确定改善措施的责任人和时间）
  │   5. 开放讨论（10 分钟，是否有遗漏）
  └─ 会议产出：定稿的复盘报告 + 行动项列表
        │
        ▼
第四步：行动项跟踪（复盘后 ─ 直到所有行动项关闭）
  ├─ 所有行动项录入追踪系统（Jira、Linear、Asana）
  ├─ 每个行动项有：负责人、截止日期、验收标准
  ├─ 每周的 SRE 例会检查行动项状态
  └─ 每个月的可靠性评审中回顾所有未关闭的行动项
```

**行动项定义规范**：

一个好的行动项不是"加强测试"或"完善监控"这样的模糊描述：

```
❌ 不合格的行动项：
  - "加强数据库监控"——太模糊，无法验证

✅ 合格的行动项：
  - "为支付数据库添加连接池使用率的 Grafana 面板和 PagerDuty 告警
    （阈值：使用率 > 80% 持续 5 分钟触发 P2 告警）
    责任人: Alice  截止: 2026-05-23  验收: PagerDuty 中告警规则已生效"
```

**行动项的分类和优先级**：

```yaml
行动项按类型分：
  - 🛡 预防性（Preventive）：修改系统防止同类故障再次发生（优先级最高）
  - 🔍 检测性（Detective）：增加监控和告警（让下次故障更快被发现）
  - ⚡ 响应性（Responsive）：改进故障响应流程（降低 MTTR）
  - 📋 流程性（Process）：改进文档、规范、培训

行动项按优先级分：
  - P0：需要在 1 周内完成
  - P1：需要在 1 个月内完成
  - P2：需要在 3 个月内完成
```

**行动项的"闭环"定义**：

一个行动项只有满足以下条件才算"关闭"：
1. 技术方案已实施并上线
2. 告警规则已生效或监控面板已可用
3. 相关的文档和 Runbook 已更新
4. 团队内已完成知识共享（如通过技术分享）

**复盘质量评估**：

如何判断一次复盘是好是坏？可以用以下问题自评：

```
Checklist:
  ┏━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━┓
  ┃  ✅ 复盘报告发布后 7 天内产生了行动项     ┃
  ┃  ✅ 行动项有明确的负责人和截止日期        ┃
  ┃  ✅ 至少 80% 的行动项在承诺的日期前完成   ┃
  ┃  ✅ 复盘报告没有"人名"（只有系统和流程）  ┃
  ┃  ✅ 复盘报告包含"做对了什么"              ┃
  ┃  ✅ 复盘会议全员参加，没有人觉得在追责    ┃
  ┗━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━┛
```

**长期趋势分析**：

单次复盘的价值有限——真正有价值的是"多次复盘的累计分析"。每季度做一次复盘趋势分析：

```yaml
Q2 2026 故障趋势分析：
  总故障数：12（较 Q1 的 18 次下降 33%）
  
  根因分类：
  - 变更相关：5 次（42%）← 重点关注
  - 容量相关：3 次（25%）
  - 外部依赖：2 次（17%）
  - 配置错误：2 次（17%）
  
  行动项完成率：87%（较 Q1 的 72% 提升）
  
  关键发现：
  - "变更相关"故障占比最高，需要强化变更审批和灰度发布
  - 外部依赖故障虽然占比低，但 MTTR 最长——需要加强依赖故障的 Runbook
```

**Follow-up Questions**:
- Q: 如果行动项长期延期（超过 2 个周期）未完成，应该怎么处理？是行动项本身不合理还是执行出了问题？
- Q: 复盘产生的行动项和日常的开发工作如何平衡？谁来为"可靠性改进"分配资源？
- Q: 如何确保复盘的"无责"文化不只是口号——当某个行动项的缺失直接导致了下次故障时，团队是否还能保持无责心态？
